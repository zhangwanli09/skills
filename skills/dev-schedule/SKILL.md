# 开发排程表生成器

把一份产品需求转成一份格式规范的开发排程表 xlsx。核心价值：**基于真实项目代码**做任务拆解、按**开发周期**预算工时、一次性套用团队模板排版。

## 工作流

### 1. 确定角色（前端 / 后端）→ 决定类别列取值

角色决定 F「类别」列怎么填，判定优先级：

1. **用户显式说明** 最高优先（"前端排程" / "帮我拆成后端任务表"）。
2. 否则 **从当前项目自动推断工程类型**：
   - `package.json` + uni-app / vue / react / 小程序 特征 → **前端**
   - `pom.xml` / `build.gradle` / `go.mod` / `*.csproj` / Spring 等 → **后端**
3. 两者都判不出，再问用户。

- 前端排程：类别 ∈ {`前端开发`, `联调`}
- 后端排程：类别 = `后端开发`（联调是前端侧概念，后端默认不产联调行）

### 2. 读入需求（多模态，不硬依赖外部技能）

- 文字 / 大纲：直接解析。
- 截图、PDF：用内置 **Read** 直接读（Read 原生支持 PDF 分页与图片视觉解析）。
- docx 等 Read 读不了的格式：若装有 `/docx` 之类技能就用，**没有就请用户粘贴正文或给截图**，不要假设这些技能存在。
- 若需求只给了工单编号 / 链接而你无法访问：请用户提供正文或截图（不绑定任何特定需求管理工具）。

### 3. 【关键】基于真实项目代码拆解，不得凭空臆想

技能是通用的、不绑定某一仓库结构。拿到需求后：

- 用 **Glob / Grep / Explore** 先探明**当前项目**的实际布局（页面、组件、API/服务层、store 等——由项目自身约定，不假设固定目录名）。
- 定位需求涉及的真身代码，据此决定：
  1. **任务怎么拆**：新建 vs 改造既有代码；能否复用现有实现（复用越多、任务越少、工时越低）。
  2. **要不要联调行**（仅前端）：所需接口是否已存在。**缺接口才补一条 `联调` 行**；接口已就绪或纯前端改动则不加。
  3. **工时怎么估**：按代码真实复杂度与可复用度校准——改现成组件 < 新建页面。
- 找不到对应代码的需求点：按「新建」处理，**不要硬编造既有结构**（这一判断写进最后的对话总结，不写进表——L 备注列留空）。

层级映射：需求 → 平台(A) → 二级模块(B) → 功能点(C) → 若干任务行(D)。
- 前端功能点常见序列：`布局/页面布局` → `查询条件/筛选` → 其他子任务 → （按需）`联调`。
- 后端按 `接口/服务/字段` 维度拆。

### 4. 估算工时（Σ 工时是决定开发周期的依据）

先按第 3 步基于真实代码复杂度**如实**给每条任务估工时（**单条取整数 1–7H，即 1 / 2 / 3 / 4 / 5 / 6 / 7**；超过 7H 的任务拆成多条），汇总出 Σ 工时 / 人日。这份估算常**反过来是领导拍板开发周期的依据**——所以**必须诚实，绝不为凑满某个周期而灌水抬高工时**，否则会误导排期决策。

开发周期是**可选参照**，按是否给了分两支：

- **给了周期**（哪怕只是领导的大致口径）：拿 Σ 跟容量对比、如实报放得下 / 富余 / 超出。容量换算：

  ```
  capacity(H) ≈ 工作日 × 7H/日 × 人数(默认 1)   # 两周≈70H，一个月≈140H
  ```

  富余就提示可再纳入其他需求或缩短工期；超出就指出超了多少、建议砍需求 / 加人 / 延期。只在合理区间内小幅取舍，不做无依据的放大或压缩。
- **没给周期**：照常出表，把 Σ 工时 / 人日作为「建议开发周期」呈现（如「约 X H ≈ Y 人日，单人约 Z 个工作日」），**不追问**。

### 5. 生成 xlsx

把拆解结果组织成 JSON（schema 见 `scripts/build_schedule.py` 头部注释），写到临时文件，然后：

```bash
python3 scripts/build_schedule.py input.json 需求排程表.xlsx
```

路径相对本技能目录根。脚本已用 PEP 723 内联声明依赖，所以装了 uv 的环境可以直接 `uv run scripts/build_schedule.py input.json 需求排程表.xlsx`，无需预装 openpyxl；用 `python3` 跑时若报 `ModuleNotFoundError: No module named 'openpyxl'`，先 `python3 -m pip install openpyxl` 再重跑。`scripts/build_schedule.py --help` 可查完整用法。

脚本已把全部排版写死（蓝色表头、等线 13pt 表头、微软雅黑 11pt 正文、thin 边框、A/B/C 纵向合并、G 默认「未开始」、冻结表头、列宽），**不要自己用 openpyxl 重画样式**。脚本会打印 JSON 摘要（行数、Σ工时、类别）。JSON 结构（`platforms → modules → features → tasks`）见脚本头部注释。

### 6. 回报总结

生成后向用户明确说明：
- **假设**：工作日数、7H/日、人数（给了周期时用于推出 capacity）。
- **Σ工时 / 人日**：给了周期就报放得下 / 超出 / 富余；没给就把它作为「建议开发周期」呈现——都不灌水，如实报。
- 输出文件路径。
- 关键估算依据（哪些任务复用了既有代码、哪些是新建、哪些补了联调）。
- 提示 I/J/K（日期、负责人）留空待用户填，工时/联调判断可微调。

## 自查

生成后可读回 xlsx 抽查：表头文案与顺序对、F 类别与角色一致（前端∈{前端开发,联调}、后端全为后端开发）、G 全为「未开始」、H 全为 1–7 的整数、A/B/C 合并分组与层级一致。
